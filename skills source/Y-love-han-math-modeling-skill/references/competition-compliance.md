## 本文件负责

本文件是 P0 当届官方规则核验、P8 格式实现、P10 合规审查和 P11 本地交付打包的唯一规范。
它规定如何获得和证明规则，不硬编码任何赛事某一届的具体页数或格式事实。

## 本文件不负责

本文件不推测当届规则、不替代主办方通知、不选择模型，也不授权外部提交。
历史经验、优秀论文样式和往届模板只能用于发现检查项，不能覆盖当前一手来源。

## 当届规则核验

先确定：

- 赛事正式名称和主办方；
- 届次、年份、赛区和参赛类别；
- 规则发布时间、修订时间和有效版本；
- 官方入口、当前通知、题目页、模板和提交系统说明；
- 是否有赛中补充通知或勘误；
- 语言、赛制、起止时间和时区。

对每个规则来源登记 Citation 与 Evidence：URL、标题、发布主体、访问时间、版本、页面或条款位置、文件哈希和访问等级。
动态网页需保存可复核的文本摘录或快照元数据。

必须核验而非假设的类别包括：

- 页数范围或上限及计算口径；
- 摘要、目录、参考文献、附录和代码是否计页；
- 纸张、字号、行距、页边距、页眉页脚和模板；
- 文件语言、命名、格式、数量和大小；
- 匿名、队号、学校、作者和致谢限制；
- 附件、支撑材料、代码和数据要求；
- 引用、原创性、协作与 AI 使用披露；
- 提交介质、时间、系统状态和替换规则；
- 答辩、演示或视频是否适用。

任何关键项无法从当届一手来源确认，标为 `official_rules_unverified` 红线：
在 P0 `competition_rules` 证据的 `verification_status` 字段登记为
`unverified`，同时把该未确认条款登记为活动红线（finding），不得以
`verified` 状态继续。不得用往届数字填空。

## 来源优先级与冲突

默认优先级：

1. 主办方当前有效规则；
2. 当前赛中补充通知或勘误；
3. 当前官方模板及其说明；
4. 当前提交系统明确提示；
5. 主办方答疑；
6. 往届资料和第三方解释。

若更高优先级明确声明后发布文件取代旧规则，按其有效范围处理。
若当前来源冲突但无法确定适用范围，登记冲突、影响和已联系渠道，进入最小阻塞。

第三方博客、培训资料、获奖论文和论坛不能解决正式规则冲突。
它们只能作为风险提示，不能支撑合规门禁。

## 规则结构化

每条规则登记：

| 字段 | 含义 |
|---|---|
| `rule_id` | 当前运行唯一 ID |
| `competition` / `edition` | 赛事与届次 |
| `source_citation_id` | 一手来源实体 |
| `source_locator` | 条款、页或页面位置 |
| `requirement` | 结构化条件 |
| `scope` | 适用赛区、题型、交付物或阶段 |
| `severity` | 违反后是否硬阻断 |
| `verification_method` | 如何从最终文件核验 |
| `checked_artifact_ids` | 被检查产物 |
| `status` | 已核实、冲突、未知、不适用 |

页数规则必须包含计数口径，而不只记录一个数字。
文件大小规则区分十进制和二进制单位；命名规则区分大小写和扩展名。

格式规则尽量使用可重现检查：PDF 页数、字体嵌入、页面尺寸、元数据、文件列表、哈希、压缩包可解压性。
视觉或语义项由人工/代理审查补充，但不能伪装成确定性程序证明。

## 匿名与身份

队号、姓名、学校、指导教师、联系方式、承诺和签名只由参赛者或官方系统提供。
AI 不推测、不补全、不从无关文件复制。

建立身份敏感词和元数据审计，覆盖：

- PDF 正文、页眉页脚、注释和隐藏层；
- 文档属性、作者字段和生成软件元数据；
- 图片 EXIF、文件路径和代码注释；
- 压缩包目录名、用户名和绝对路径；
- Git 或编辑器痕迹；
- 支撑材料中的样例账号与个人信息。

匿名要求与引用作者不同：学术引用通常不是参赛者身份。
检查器应基于规则和位置区分，避免删除必要引用。

身份字段缺失时可生成占位说明给用户，但占位内容不得进入最终候选包。
最终打包前所有身份占位和未解析标记必须为零。

## P8 P10 P11 复核

规则在多个阶段复核，因为稿件和通知都可能变化：

### P8

- 模板、页面、语言、匿名和引用在稿件源与渲染稿中实现；
- 论文和支撑材料的实际文件类型、结构和编译警告可见；
- 所有规则引用仍指向当前有效版本。

### P10

- 独立合规角色逐条核对 rule ID 和实际产物；
- 检查 PDF 渲染、元数据、图表可读性和匿名泄露；
- 检查赛题响应矩阵与官方交付要求；
- 当前通知更新时使旧合规报告陈旧。

### P11

- 对最终实际文件重新计算页数、尺寸、文件名、格式和哈希；
- 检查压缩包能在新目录解压；
- 解压后逐项与 delivery manifest 比较；
- 候选包不得依赖项目外绝对路径；
- 只在 P11 通过并推进后生成 final 本地包标签。

规则核验不能只在 P0 做一次。

## 本地打包

打包使用显式白名单，而不是“复制整个项目再排除几个目录”。
manifest 对每个文件记录规范相对路径、SHA-256、字节数和角色。

通常允许的角色：

- 最终 PDF；
- 官方要求的源稿或表格；
- 可运行源代码；
- 配置和环境说明；
- 允许提交的数据或数据说明；
- 结构化结果和必要侧车；
- 复现说明；
- 官方要求的支撑材料；
- 适用的答辩材料。

默认禁止打包：

- `.mmflow/` 内部账本和 Registry；
- 测试夹具、恶意样本和 demo；
- 归档内容；
- 内部审查草稿和未关闭 finding；
- 缓存、临时文件、编译中间文件和失败沙箱；
- 身份信息或受限数据；
- 绝对路径、凭据、token 和环境秘密。

当届规则未要求支撑材料且全部代码与数据说明已包含在论文附录时，允许清单可以不含支撑材料项；此豁免须在 delivery manifest 或交付说明中显式注明理由，不得静默缺省。

候选包和最终包使用不同文件名，均不得覆盖已有文件。
包输出位于项目内明确交付目录，路径不得含 `..` 或重解析逃逸。

## 外部提交边界

本地生成经校验交付包与外部提交严格分离。
除非用户另行明确授权具体目标和动作，本 skill：

- 不登录提交系统；
- 不上传文件；
- 不点击最终确认；
- 不发送邮件或消息；
- 不支付费用；
- 不代签承诺；
- 不公开参赛者身份。

即使状态为 `COMPLETE`，也只说明本地包通过当前核验。
用户仍应在官方系统中确认截止时间、上传状态和最终预览。

若用户后续授权外部提交，必须在执行前再次核对目标、文件哈希和不可逆影响；该授权不由本规范自动推导。

## 阶段验收

P0、P8、P10 和 P11 相关门禁必须证明：

- 赛事、届次、有效规则版本和一手来源可识别；
- 页数、匿名、文件名、附件、AI 披露和提交要求均有结构化 rule；
- 来源冲突已按优先级解决或合法阻塞；
- 队号、身份和签名没有被 AI 推测；
- 最终 PDF 与支撑材料按实际文件复核，而非检查模板文字；
- delivery manifest 与解压后的包逐文件一致；
- 内部状态、demo、测试、归档、秘密和受限数据未进入包；
- 没有执行未授权的外部提交。

任何当届硬规则未知、冲突或违反时，发布状态必须是 `NOT_READY`。


## 附录：v2 规则驱动合规

### 结构化要求

- `competition_rules` 的 `requirements` 必须是结构化列表：`requirement_id`（唯一）、`kind`（boolean/number/string/pattern/list）、`value`（类型与 kind 一致）、`scope`、`severity`（HARD/SOFT）、`source_citation_id`、`snapshot_artifact_id`、`source_locator`、`verification_method`。
- P0 门禁校验该结构；程序不能静态假设"所有比赛都要 PDF"或固定页数，页数、文件名、匿名、大小、源稿与支撑材料都由当届要求驱动。

### 合规引擎

- `compliance.py` 按 requirement 逐条映射到真实项目事实：`pdf_required` 检查 production PDF artifact；页数要求读取实际 PDF 的页对象；文件名要求匹配 artifact 名；大小要求读取文件字节；匿名要求隐私扫描通过。没有程序化验证方法的 HARD 要求报告 FAIL。
- P10 门禁重算引擎输出并与注册的 `compliance_report.requirement_checks` 逐项比对，自报 status=PASS 不能替代引擎事实。

### 交付与隐私

- delivery manifest 每项可声明独立 `archive_path`（zip 内成员名），禁止项目内部运行路径泄露。
- 打包命令自动登记 production package artifact，并在新临时目录安全解压核验（zip-slip、绝对路径、驱动器路径、保留设备名、大小写冲突、成员哈希、入口文件存在）。
- `scan-privacy` 扫描 PDF 元数据、隐藏文本、DOCX 属性、图片 EXIF、绝对路径、API key/token/私钥、.git/编辑器缓存、嵌套压缩包；P11 门禁重算扫描并与注册证据比对。
- 最终包必须与通过 P11 的候选包字节一致；字节变化必须重新进入 P11。

### requirement_id 命名约定（合规引擎匹配规则）

`compliance.py::evaluate_requirements` 依据 requirement_id 中的保留词干
选择程序化验证路径；命名不当的 HARD 要求一律 FAIL，不会静默跳过。
登记 requirements 前按下表命名：

| 保留词干（requirement_id 小写包含） | 触发验证 | 示例 requirement_id |
|---|---|---|
| `pdf` 且 kind=boolean value=true | 存在 production PDF artifact | `submission.pdf_required` |
| `anonymous` | 隐私扫描证据状态为 PASS | `submission.anonymous_required` |
| `source`（且不含 `pdf`） | 存在 production 源稿/源码 artifact | `submission.source_code_required` |
| 含 `page` 且含 `min` 或 `max`（kind=number） | 解析实际 PDF 页数比较 | `submission.page_max` / `submission.page_min` |
| 含 `size`（kind=number） | PDF 文件字节数上限比较 | `submission.file_size_max_bytes` |
| kind=pattern | 对全部 VALID artifact 文件名做正则匹配 | `submission.pdf_filename` |
| kind=boolean value=false | 显式不要求，直接 PASS | `support.zip_not_required` |

**匿名要求的时序纪律**：privacy_scan 证据允许在 P10 与 P11 登记阶段
（`evidence-v1.json::evidence_stage_matrix`）。当届规则登记了 `anonymous`
词干要求时，必须在进入 P10 门禁**之前或期间**运行 `scan-privacy` 并登记
privacy_scan 证据，否则合规引擎对匿名要求报 FAIL、P10 无法通过；P11
门禁会重扫并要求与已登记证据完全一致，交付包字节变化后按 P11 纪律失效旧
证据并在新 epoch 重登。禁止为绕过该检查把匿名要求改名为不含保留词干的
标识符——那会落入 manual_check FAIL（HARD）或静默 PASS（SOFT），两种结果
都不构成真实合规。

其余命名（无任何词干命中）：manual_check 方法返回 FAIL（HARD）/WARNING
（SOFT）。页数统计优先使用 pypdf/PyMuPDF 解析（对压缩对象流正确），
解析不可用时回退 `/Type /Page` 字节扫描。
