## 本文件负责

本文件是 P1 材料清点与选题、P2 需求矩阵、Problem Contract、歧义分支、小问依赖和外推边界的唯一规范。
它把自然语言赛题转换为后续模型、数据、验证和论文可以机器引用的结构化合同。

## 本文件不负责

本文件不替代当届官方规则核验，不选择具体算法，不给出统计适配器，也不判断论文格式。
题意形式化必须先于模型偏好；不能因为熟悉某算法而把题目改写成该算法擅长的问题。

## 材料清点

建立输入清单，逐项登记：

- 规范相对路径和文件类型；
- 来源、下载位置或用户提供说明；
- SHA-256 与字节数；
- 是否为赛题正文、附件、数据字典、补充通知或模板；
- `read_status`：未读、部分读取、完整读取、无法读取；
- 解析方式与解析质量；
- 与哪些题目或小问相关；
- 是否存在缺页、损坏、密码、扫描 OCR 或版本冲突；
- 缺失是否阻断可靠作答。

赛题正文必须按页、段、表、图或题目编号建立来源锚点。
后续 Requirement Matrix 的每个要求都引用锚点，不引用“我记得题目说”。

表格、图片和公式不能只依赖纯文本抽取。
对关键图表执行视觉或结构核对；OCR 结果需抽查数字、小数点、上下标、单位和负号。

若明确存在附件却未收到，先查本地项目、用户给定范围和一手公开来源。
附件不影响问题识别时可继续安全部分；决定目标变量或约束时进入最小阻塞，不能用猜测补齐。

## 选题决策

多题赛事建立可审计选择记录，至少考虑：

1. 题目要求是否完整可理解；
2. 数据和必要外部资料是否可合法获得；
3. 核心结论是否可验证、反证或复现；
4. 计算资源是否足以执行最低可信方案；
5. 是否存在清楚的基线和改进路径；
6. 是否能产生决策相关而非装饰性的洞察；
7. 领域风险、合规风险和时间风险；
8. 小问之间是否共享证据，还是存在互相冲突的假设。

先排除硬失败项，再比较剩余候选。
不得用固定加权总分让“数据不可得”被“视觉潜力高”抵消。
选择记录列出候选、否决理由、选中项、撤销条件和触发重新选题的阈值。

单题赛事把“选题”登记为规则化 `NOT_APPLICABLE`，依据是官方赛制和清单中的候选数，而不是空白说明。
仍需完成材料完整性和可解性评估。

## 需求矩阵

需求矩阵把赛题转成不可遗漏的响应单元。
每行至少含：

| 字段 | 含义 |
|---|---|
| `requirement_id` | 当前运行内唯一标识 |
| `source_anchor` | 赛题原文精确位置 |
| `source_text` | 最小必要原文摘录 |
| `requirement_type` | 显性、隐含、格式、数据、交付或评价 |
| `interpretation` | 数学化解释 |
| `deliverable` | 必须产出的答案、图、表、模型、代码或文件 |
| `acceptance_evidence` | 什么实体能够证明已回应 |
| `dependencies` | 前置要求和数据 |
| `ambiguity_ids` | 相关歧义分支 |
| `response_claim_ids` | P7 后绑定的主张 |
| `manuscript_locator` | P8 后的论文位置 |
| `status` | 未处理、处理中、已证实回应、阻塞或规则化不适用 |

显性要求来自命令式问题、给定输出和硬约束。
隐含要求来自评价对象、单位、时间信息集、可行性、比较基准、解释责任、决策对象和交付语境。
不得把“构建模型”理解为只给公式；通常还隐含输入、求解、验证和适用范围。

把评分对象与交付对象分开。
评分对象可能是预测精度、解释力、可行性或建议质量；交付对象可能是论文、代码、数据表和答辩材料。
一个漂亮模型不能替代题目明确要求的清单、建议或方案。

## Problem Contract

每个小问或可独立验证的问题建立一个 Problem Contract。
合同至少定义：

- `problem_id` 与来源要求；
- 决策者、分析单位和目标对象；
- 任务标签与预期主张类型；
- 可用输入、信息时点和禁止使用的信息；
- 输出变量、单位、精度和交付形式；
- 状态变量、决策变量、参数和随机量；
- 硬约束、软约束、边界和可行域；
- 时间、空间、主体、群组和重复测量尺度；
- 主指标、次指标、比较方向和不可比较条件；
- 数据划分单位和泄漏边界；
- 模型族候选与必须验证的性质；
- 允许主张、禁止主张和外推范围；
- 与其他问题、结果和交付项的依赖。

结构示例只展示合同，不包含结果：

```json
{
  "problem_id": "Q1",
  "traits": ["temporal", "grouped", "constrained"],
  "claim_types": ["forecast", "optimization_recommendation"],
  "model_families": [],
  "properties": {},
  "hard_constraints": [],
  "dependencies": []
}
```

注意：Problem Contract 没有 `task_types` 字段——任务语义一律通过 `traits`、
`claim_types`、`model_families` 与 `properties` 表达；适配器选择也只消费这四个键。

单位必须在变量层声明，不能到论文阶段再猜。
维度不一致、时间信息穿越或决策变量与观测变量混淆均在 P2 解决。

“最优”“显著”“因果”“稳健”“普适”等词必须预先转成可检查的主张合同。
若没有相应证据路径，只允许使用更弱表述。

## 任务与主张标签

任务可以多标签，不强迫单选：

- 描述：概括当前或历史结构；
- 预测：对未见样本或未来做点预测；
- 概率预测：输出分布、区间或事件概率；
- 解释：描述模型内部或变量关系，不自动具有因果性；
- 因果：定义干预、反事实或效应 estimand；
- 参数估计与统计推断：估计总体量和不确定性；
- 优化：在约束下搜索决策；
- 优化建议：把数学解转换为行动并考虑偏好；
- 综合评价或排序：聚合多指标；
- 仿真：通过机制或随机过程生成系统行为；
- 理论：推导命题、界、性质或解析表达；
- 情景分析：在明确假设下比较条件变化；
- 聚类、网络、空间、ODE/PDE 等结构标签。

标签直接决定验证适配器。
例如 `temporal + forecast` 要求时间信息集和回测；`constrained + global_optimum` 要求可行性和界。
不能用“机器学习题”这种宽泛标签替代合同。

**受控词表映射（写入 Problem Contract 前必须核对）**：
Problem Contract 的 `traits`、`claim_types`、`model_families` 只接受引擎受控
词表（P2 语义检查会拒绝未知键）。上表的自然语言标签按以下方式归一。

⚠️ 两套词表同名不同物，严禁混用：
- **Contract.claim_types**（本表）：适配器词表，合法值以
  `python scripts/mmflow.py adapters --json` 输出为准（forecast、
  probabilistic_forecast、causal、optimization_recommendation、global_optimum、
  parameter_estimate、scenario、ranking、spatial_prediction、theoretical）；
- **Claim Registry 的 claim_type**：主张类型词表（computed、observational、
  inferential、theoretical、external、recommendation、limitation，见
  `references/evidence-and-claims.md`），只在 P7 `register-claim` 时使用。
  把 `observational` 写进 Problem Contract 会直接导致 P2 语义检查 FAIL。

| 本节自然语言标签 | 写入合同的受控键 |
|---|---|
| 描述/概括 | 不占用 Contract.claim_types；描述性结论在 P7 以 Claim Registry 类型 `observational`/`computed` 登记 |
| 预测 | `forecast` |
| 概率预测 | `probabilistic_forecast` |
| 解释 | 同"描述/概括"：P7 以 Claim Registry 类型承载；Contract 层不使用独立标签 |
| 因果 | `causal` |
| 参数估计与统计推断 | `parameter_estimate` |
| 优化 / 优化建议 | `optimization_recommendation`；有最优性主张加 traits `constrained`、claim `global_optimum` |
| 综合评价或排序 | `ranking` + model_families `composite_evaluation` |
| 仿真 | `scenario` + model_families `simulation` |
| 理论 | `theoretical` |
| 情景分析 | `scenario` |
| 聚类 / 网络 / 空间 | 作为 model_families：`clustering` / `network`；空间另加 traits `spatial` 或 claim `spatial_prediction` |
| ODE / PDE | model_families `ode` / `pde` |
| 博弈论（均衡、极小极大） | model_families `analytic_model` + claim `theoretical` 或 `ranking`；数值演化博弈用 `simulation` + claim `scenario` |
| 排队论 / 随机服务系统 | traits `stochastic` + model_families `simulation`；claim `scenario` 或 `forecast` |
| 可靠性 / 生存分析 | model_families `analytic_model` + claim `parameter_estimate` |
| 图论与组合优化 | traits `constrained` + model_families `exact_optimization`（有界/小实例）或 `heuristic_optimization`（无证书算法） |
| 多准则决策 / 效用权衡 | claim `ranking` + model_families `composite_evaluation` |

完整机器名与适配器对照随时可用
`python scripts/mmflow.py adapters --json` 输出；
逐字段契约见 `references/evidence-registration-cookbook.md`。

## 歧义管理

每个影响模型、数据、约束或答案的歧义建立记录：

1. `ambiguity_id` 和来源锚点；
2. 至少两个合理解释；
3. 每个解释产生的可检验预测或不同交付；
4. 支持或反对它的题面、数据、规则或领域证据；
5. 当前选择、并行保留或阻塞决定；
6. 决定的撤销条件；
7. 对下游实体和计算预算的影响。

优先选择可由题面和数据区分的解释。
无法区分但影响小的歧义做情景分支；影响核心目标且结论相反时，在论文中披露或请求最小澄清。
不得悄悄选择更容易建模的解释。

歧义示例：题目说“效率提高”，可能指单位时间产出，也可能指单位资源产出。
两种解释具有不同单位、目标函数和数据要求，必须在合同中分开，不能只在文字中解释一次。

## 赛题陷阱识别参考

形式化完成后对五类常见陷阱做一轮显式排查，命中项进入歧义记录或 Problem Contract 对应字段：

| 陷阱 | 典型表现 | 合同落点 |
|---|---|---|
| 假复杂真解析 | 题面暗示仿真或优化，实际存在解析解、封闭形式或守恒量 | 复核任务标签；候选基线中加入解析对照 |
| 隐约束 | 未明说的物理限制、非负性、整数性、容量或政策边界 | 约束字段补全并标注来源位置 |
| 数据冗余 | 多列高度共线或同一量的不同口径重复给出 | 变量表标注派生关系，防止双重计入 |
| 公式有误 | 题给公式存在笔误、量纲不一致或符号未定义 | 登记歧义，按两种读法建立情景分支 |
| 评价歧义 | 指标方向、比较基准或排名规则不明 | 评价指标字段显式声明方向与基准 |

排查结论写入需求矩阵备注或决策摘要；确认无命中时在决策摘要中注明已排查即可，不设额外登记负担。

## 依赖与统一框架

建立小问依赖 DAG，边的含义必须明确：

- 数据依赖：后问使用前问清洗或估计的实体；
- 参数依赖：后问使用前问参数及不确定性；
- 约束依赖：前问发现转成后问可行域；
- 评价依赖：前问指标用于后问比较；
- 叙事依赖：只共享背景，不构成计算血缘。

依赖关系必须进入 Lineage，而不是仅画技术路线图。
上游结果变化时，状态传播到所有真正依赖的后问。

统一框架只有在共享变量、尺度、假设和验证语义相容时采用。
统一可以减少重复并揭示耦合，但不能强行把预测、因果和价值判断塞进同一目标函数。
若不同小问需要互斥的数据生成假设，保持模块化模型并用明确接口连接。

先检查循环依赖。
若 Q2 的目标定义依赖 Q3 的结果，而 Q3 又使用 Q2 的决策，应改写为联合问题、迭代固定点或明确外层情景，而不是留下隐式循环。

## 外推边界

合同必须区分：

- 样本内描述；
- 与训练分布相同的未见样本；
- 时间外推；
- 空间外推；
- 新主体或新群组；
- 结构变化后的情景；
- 因果干预；
- 机制参数超出校准范围。

允许外推必须有支持：模型结构、领域约束、覆盖设计、漂移分析或外部验证。
仅在给定样本上拟合良好，不允许声称对未来、异地或干预有效。

在合同中列出禁止外推区域和触发降级的条件。
例如新场景超出训练支持时，只能给出情景演算或不确定性扩大的探索性结果，不能维持确认性精度主张。

## 阶段验收

P1 通过前必须登记完整 input inventory 和选题记录；单题不适用必须有规则证据。
P2 通过前必须证明：

- 每个赛题要求都有来源锚点和验收证据类型；
- 每个小问都有完整 Problem Contract；
- 单位、尺度、信息时点和硬约束无未解决矛盾；
- 任务与主张标签足以选择验证适配器；
- 关键歧义有分支、证据和撤销条件；
- 小问依赖形成无环、语义清楚的 DAG；
- 外推与禁止外推边界明确；
- 缺失关键材料时已进入结构化最小阻塞，而非填入虚构信息。

形式化文件的章节齐全不能自证通过；门禁必须解析结构化字段并验证引用实体。
